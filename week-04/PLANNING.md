# Week 04 — Multi-Agent 협업 및 워크플로 상태 관리

## 1. 한 줄 요약
에이전트 하나에게 모든 일을 맡기지 않고, **기획(Planner) → 조사(Researcher) → 검수(Reviewer)** 로 역할을 나누어 순차적으로 작업하고 검증하는 **멀티 에이전트 워크플로**를 구축했다.

## 2. 왜 멀티 에이전트인가? (실무 관점)
- **단일 에이전트의 한계**: 혼자서 계획도 세우고, 검색도 하고, 답변까지 쓰다 보면 중간에 조건을 빠뜨리거나 자의적으로 환각(거짓 답변)을 덧붙이는 일이 자주 발생한다.
- **역할 분담의 효과**:
  - **Planner**: 사용자 질문이 무엇을 요구하는지 먼저 단계별로 쪼갠다.
  - **Researcher**: 세운 계획대로 3주차 도구(RAG 문서, DB)를 돌려 사실(Fact)만 가져온다.
  - **Reviewer**: 가져온 사실이 질문 의도에 맞는지, 환각이나 잘못된 정보가 없는지 마지막으로 확인하고 승인한다.
- **상태 머신(State Machine)의 필요성**: LangGraph처럼 `START → PLAN → RESEARCH → REVIEW → FINISH` 로 이동하는 명확한 순서도를 코드로 짜두어야 에이전트들이 딴길로 새지 않고 흐름대로 움직인다.

## 3. 구조 (아키텍처)
```
[사용자 요청] ("김철수 연차 조회 후 메일 송신해줘")
      │
      ▼
 ┌─────────┐     계획 수립
 │ PLAN    │ ───────────────────────┐
 └─────────┘                        │
      │                             ▼
      ▼                     ┌───────────────┐     근거 수집 (RAG / DB)
 ┌───────────┐              │ RESEARCH      │ ────────────────────────┐
 │ RESEARCH  │ ──────────►  └───────────────┘                         │
 └───────────┘                      │                                 ▼
      │                             ▼                         ┌───────────────┐
      ▼                     ┌───────────────┐    검수 & 통과   │ REVIEW        │
 ┌───────────┐  재조회 요청 │ REVIEW        │ ──────────────► └───────────────┘
 │ REVIEW    │ ───────────► └───────────────┘                         │
 └───────────┘                      │ (최대 2회 재시도)               ▼
      │                             ▼                         ┌───────────────┐
      └─────────────────────────────────────────────────────► │ FINISH        │
                                                              └───────────────┘
```

## 5. 만들어보며 겪은 실수 노트 (중요)

> 코드를 짜면서 막혔던 지점들과 해결 방법입니다.

| # | 문제 현상 | 왜 발생했나? | 이렇게 해결함 |
|---|-----------|--------------|---------------|
| 1 | **에이전트끼리 대화가 끝나지 않음** | Reviewer가 맘에 안 든다고 빠꾸(Reject)를 계속 시켜 루프에 갇힘 | `max_revisions = 2` 로 재시도 횟수 제한을 걸어 무한 루프 방지 |
| 2 | **Planner가 세운 계획을 Researcher가 안 읽음** | 이전 단계의 결과물(State)이 다음 에이전트에 파라미터로 안 넘어감 | 전역 `State` 객체를 만들어 에이전트 간 주고받는 구조로 고침 |
| 3 | **Reviewer가 그냥 다 통과시켜버림** | 검수 기준이 모호해서 아무 텍스트나 들고 와도 승인함 | 최소 수집 데이터 개수와 에러 메세지 유무를 체크하는 판정 조건 추가 |
| 4 | **에이전트가 많아져서 속도가 느려짐** | 한 번에 처리할 일도 3단계를 거치다 보니 시간이 수 초 더 걸림 | 필요 이상으로 에이전트를 쪼개지 않고 핵심 3개 역할로 단순화 |
| 5 | **중간 과정이 안 보여서 디버깅이 어려움** | 최종 답변만 출력되니 중간에 어떤 에이전트가 틀렸는지 모름 | `history_logs` 배열에 노드별 실행 기록을 쌓아 JSON으로 반환 |
| 6 | **API 키가 없을 때 멀티 에이전트가 동작 안 함** | 외부 API에 종속되면 로컬 테스트가 막힘 | 도구 실행과 검수 과정을 로컬에서 바로 확인 가능한 Mock 오케스트레이터 구성 |
| 7 | **Researcher가 불필요한 도구까지 다 호출함** | Planner의 계획과 무관하게 자기가 가진 모든 도구를 한 번씩 돌림 | 요청 문맥(키워드)에 맞는 도구만 선별 호출하도록 분기 조건 작성 |
| 8 | **State 상태값 변경이 꼬임** | 여러 함수에서 State를 임의로 수정하다가 이전 기록이 덮어씌워짐 | 오케스트레이터 중앙 제어 함수에서만 State 전이를 처리하도록 단일화 |
| 9 | **Rejection 발생 시 처음부터 다시 시작함** | 검수 실패 시 PLAN 단계로 돌아가서 처음부터 다시 계획을 세움 | 실패 시 PLAN이 아닌 RESEARCH 단계로 돌아가 조사를 보완하도록 효율화 |
| 10 | **에러가 나도 통과된 것처럼 표시됨** | 도구 실행 중 예외(Exception)가 났는데 텍스트로 뭉개서 넘김 | 도구 에러 발생 시 `[Tool Exec Error]` 키워드를 붙여 Reviewer가 감지하게 함 |
