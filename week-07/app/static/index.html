1. TypeSafe AI Jev (`typesafe-sdk`) 표준 코드 패턴

      
from typesafe_sdk import Choice, Noul, Score, TypeSafeClient

# TYPESAFE_API_KEY 환경변수 자동 참조
with TypeSafeClient() as client:
    response = client.system_one(
        model="jev-latest",
        state=support_ticket_state,
        questions={
            "department": Choice(
                instructions="Which team should handle this request?",
                criteria={
                    "billing": "Payment, duplicate charge, or refund issues",
                    "technical_sre": "Production outage, API 504 timeout, DB issues",
                    "security_cert": "Account takeover, suspicious IP, prompt injection",
                },
            ),
            "severity": Score(
                instructions="Rate the operational severity of this issue.",
                criteria=[
                    "Routine inquiry",
                    "Minor functional issue",
                    "Urgent operational impact",
                    "Critical production outage or breach",
                ],
            ),
            "refund_requested": Noul(
                instructions="Does the customer explicitly request a financial refund?"
            ),
        },
    )

# 강타입 결과 및 확률/신뢰도 기반 결정론적 제어 흐름
if response.answers["department"].confidence < 0.55:
    escalate_to_human_queue(response.answers["department"].probabilities)
elif response.answers["department"].choice == "billing" and response.answers["refund_requested"].noul >= 0.70:
    trigger_automated_refund_pipeline()

    


    

      
2. 직접 만들어보며 겪은 10가지 실수 노트 (Troubleshooting)

      

        
          

            #
            문제 현상
            왜 발생했나? (원인)
            이렇게 해결함 (해결책)
          

        
        
          

            1
            생성형 LLM으로 라우팅 구현 시 `json.loads` 파싱 장애
            LLM이 JSON 앞뒤에 설명 문구(`Here is the JSON:`)를 붙이거나 프롬프트 인젝션으로 스키마 외 키를 생성함
            자유 텍스트를 생성하지 않는 System One 모델(TypeSafe AI Jev)의 `Choice`, `Score`, `Noul` 강타입 프리미티브로 전환
          

          

            2
            복합 문의(요금제+기술+보안)를 잘못된 부서로 자동 배정
            최고 확률 1순위(`choice`) 값만 보고 `confidence`(결정 신뢰도)를 확인하지 않아 모호한 티켓도 강제 라우팅함
            `department.confidence < 0.55`일 때는 자동 배정을 멈추고 전체 확률 분포표를 첨부해 HITL(사람 검토 큐)로 에스컬레이션
          

          

            3
            순서가 있는 심각도(Severity)를 `Choice`로 잘못 모델링
            `Choice`는 순서가 없는 범주형이어서 1단계와 3단계에 확률이 나뉠 때 중간 기대값을 계산할 수 없음
            서열 척도 전용 프리미티브인 `Score`를 사용하여 확률 가중 연속 기대 점수($E[S] = \sum i \cdot P_i$)로 정밀 평가
          

          

            4
            Yes/No 판별을 `Choice(["yes", "no"])`로 불필요하게 중복 정의
            단순 참/거짓 조건 검증에 다지선다 구조체를 쓰면 코드 가독성과 임계값 직관성이 떨어짐
            이진 확률 전용 프리미티브인 `Noul`을 사용하여 `response.answers["refund"].noul >= 0.70` 형태로 간결화
          

          

            5
            여러 질문을 루프(`for`)로 4번 나눠 호출하여 Latency 4배 증가
            `department`, `severity`, `refund`, `security`를 각각 별도 API 요청으로 직렬 호출함
            `client.system_one(state=..., questions={...})`의 `questions` 딕셔너리에 묶어 **단일 병렬 패스(Single Parallel Pass)**로 1회 호출
          

          

            6
            프롬프트 인젝션 공격이 포함된 티켓을 System 2 LLM에 바로 전달
            가드레일 없이 생성형 LLM이 사용자 원문을 먼저 요약/답변하게 하여 시스템 프롬프트 탈취 위험 노출
            System 1(Jev)의 `security_risk` `Noul` 게이트를 최상단(Gate 1)에 배치하여 임계값 초과 시 System 2 호출을 원천 차단
          

          

            7
            `Score` 루브릭 기준(`criteria`)의 순서를 뒤섞어 작성
            루브릭 리스트에 `[높음, 낮음, 중간]`처럼 서열 순서를 지키지 않아 가중 평균 점수의 의미가 왜곡됨
            반드시 가장 낮은 단계(0점)부터 가장 높은 단계(N-1점)까지 단조 증가 순서로 `criteria`를 정렬
          

          

            8
            `Choice` 옵션 이름만 간략히 적고 판단 기준(`criteria` 설명) 누락
            옵션 키(`["t1", "t2"]`)만 전달하면 모델이 도메인 맥락을 정확히 구분하지 못해 확률이 분산됨
            `criteria={"billing": "결제 오류, 중복 청구 및 환불...", "technical_sre": "..."}`처럼 명확한 기준 설명을 함께 제공
          

          

            9
            확률 분포 반올림 오차로 인해 옵션 확률 합계가 `0.9999` 또는 `1.0001`이 됨
            부동소수점 Softmax 계산 후 소수점 4자리 반올림 시 미세 오차 발생
            최대 확률 항목에 `1.0 - sum(probs)` 잔차를 보정하여 확률 합계가 정확히 `1.0`을 만족하도록 정규화
          

          

            10
            `TYPESAFE_API_KEY` 미보유 환경에서 실습 및 테스트 불가
            외부 클라우드 SDK에만 의존하면 오프라인이나 키 미발급 환경에서 파이프라인 검증이 불가능함
            Softmax 확률 분포, 섀넌 엔트로피 기반 Confidence, 루브릭 기대값 수식을 내장한 로컬 확률 추론 엔진을 함께 구현
